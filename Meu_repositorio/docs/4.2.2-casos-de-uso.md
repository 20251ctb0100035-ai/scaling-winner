# 4.2.2 Modelagem de Casos de Uso

## Atores

Dois papéis usam o DoceAgenda. O ator o papel, não a pessoa. Nas histórias da 4.2.1 a cliente Mariana fala com confeiteira. No diagrama o ator é **confeiteira**, como está em "Quem usa" da 4.1.

Quem opera o sistema é o ator, mesmo quando outra pessoa se beneficia. Na HU02 quem fala é o cliente, mas quem  o pedido do cliente no balcão é o confeiteira. Por isso a devolução é um caso de uso do .

| Ator | Quem é | O que faz no sistema |
|---|---|---|
| Cliente | quem agenda e faz o pedido | consulta se um livro está disponível |
| Confeiteira | quem atende o pedido. | Registra clientes, cadastra produtos do cardápio, lança encomendas e atualiza de produção e entrega. |

## Casos de uso

Cada caso de uso é um objetivo que um ator alcança no sistema. O nome é o mesmo do requisito que ele atende, letra por letra.

Nem todo requisito vira elipse. O RF07 (Calcular data de devolução) é algo que o sistema faz no meio de um empréstimo, não um objetivo que alguém vem ao balcão alcançar. Ele aparece como passo da especificação, mais abaixo.

| Caso de uso | Ator | Atende |
|---|---|---|
| Cadastrar pedido | confeiteira | RF01 |
| atender Cliente | confeiteira | RF02 |
| Disponibilidade do pedido | Cliente | RF03 |
| Registrar pedido | confeiteira | RF05 e RF07 (o cálculo da data é o passo 5 do fluxo principal) |
| Identificar cliente | nenhum: é incluído por Registrar pedido e Registrar Reembolso | passo que os dois compartilham, sem requisito próprio |
| Registrar devolução | confeiteira | RF04 |
| Listar atrasos | confeiteira | RF06 |

## Especificação do caso de uso principal

Registrar encomenda é o caso de uso que o sistema existe para fazer: é ele que tira a encomenda do caderninho. Por isso é o especificado.

| Campo |  |
| --- | --- |
| Caso de uso | Registrar encomenda |
| Ator | Confeiteira |
| Pré-condição | O produto e o cliente estão cadastrados (RF01 e RF02), e a confeiteira está identificada no sistema (RNF02). |
| Pós-condição | A encomenda está registrada com a data de entrega, e o produto aparece como indisponível na consulta (RF03). |

**Fluxo principal**

1. A confeiteira identifica o cliente, pelo nome ou pelo telefone («include» Identificar cliente).
2. O sistema mostra o cadastro do cliente e confirma que ele não tem encomenda atrasada.
3. A confeiteira informa o produto.
4. O sistema confirma que o produto está disponível.
5. O sistema calcula a data de entrega, sete dias a partir da data de hoje (RF07).
6. A confeiteira confirma a encomenda.
7. O sistema registra a encomenda e marca o produto como encomendado.

**Fluxo alternativo**

* **A1, no passo 2: o sistema não encontra o cliente.** A confeiteira cadastra o cliente (Cadastrar cliente, RF02) e o fluxo volta ao passo 1.

**Fluxos de exceção**

* **E1, no passo 2: o cliente tem encomenda atrasada.** O sistema avisa qual produto está atrasado e não registra a encomenda. O caso de uso termina sem a pós-condição. ❓ A confirmar com a cliente: hoje a confeiteira aceita encomendas de quem está atrasado?
* **E2, no passo 4: o produto está indisponível.** O sistema informa até quando ele está reservado para outro cliente e não registra. O caso de uso termina sem a pós-condição.

A diferença entre A1 e E1 está no fim. No fluxo alternativo, a encomenda acontece por outro caminho. Na exceção, ela não acontece.

| Requisito | Caso de uso | Onde aparece |
| --- | --- | --- |
| RF01 Cadastrar produto | Cadastrar produto | elipse, e pré-condição de Registrar encomenda |
| RF02 Cadastrar cliente | Cadastrar cliente | elipse, e fluxo alternativo A1 |
| RF03 Consultar disponibilidade | Consultar disponibilidade | elipse, e pós-condição de Registrar encomenda |
| RF04 Registrar entrega | Registrar entrega | elipse |
| RF05 Registrar encomenda | Registrar encomenda | elipse e especificação |
| RF06 Listar atrasados | Listar atrasados | elipse |
| RF07 Calcular data de entrega | nenhuma elipse | passo 5 do fluxo principal de Registrar encomenda |

**Todo requisito tem lugar.** Seis viraram elipse com o mesmo nome. O RF07 não virou, e a tabela diz onde ele mora.

**Toda elipse tem requisito.** Nenhum caso de uso apareceu sem um requisito por trás. Se aparecesse, seria sinal de requisito faltando na 4.2.1, e o conserto seria lá. A exceção é Identificar cliente, que existe pelo «include» e não por um requisito.

**O que a especificação mudou.** Escrever o fluxo mostrou uma regra que a 4.2.1 não tinha: o que fazer com o cliente atrasado. Ela ficou anotada com ❓ na exceção E1, para a próxima conversa com a confeiteira.
